# Khozo System Audit

Date: 2026-06-04

## Reference Systems Studied

- TrackChild / Mission Vatsalya, Government of India: national missing and vulnerable child tracking, with police, Child Welfare Committee, Child Care Institution, Juvenile Justice Board, District Child Protection Unit, railway/RPF, and state/national admin stakeholders.
- KhoyaPaya, Government of India: citizen-facing missing/found child reporting that feeds institutional review rather than exposing sensitive identity details publicly.
- GHAR, NCPCR / Government of India: digital monitoring of child restoration and repatriation workflows, including institutional handover, transfer, and support needs under Juvenile Justice protocols.
- Mission Vatsalya grievance/feedback: public complaint and feedback reference tracking routed to CCI, DCPU, CWC, SCPS/state, or Ministry-level desks.
- Mission Vatsalya / TrackChild / NCRB identity linkage: operational case workflows use external IDs from TrackChild, Khoya-Paya, NCRB/SCRB, CCTNS/FIR, GHAR, or state portals for cross-system traceability.
- Mission Vatsalya welfare services: child-protection follow-up can include sponsorship care, foster care, adoption facilitation, aftercare, counselling, medical, education, and family-strengthening referrals.
- Juvenile Justice / Mission Vatsalya casework artifacts: Social Investigation Reports, Individual Care Plans, family/risk assessments, and rehabilitation plans are formal welfare records that should be attached to child-protection cases.
- Mission Vatsalya citizen onboarding: public registration should verify mobile ownership with OTP before creating citizen or NGO accounts.
- Juvenile Justice production tracking: rescued children should be produced before CWC/JJB or appropriate authority within statutory timelines, with production outcome and next action recorded.

## Current Strengths

- Covers the main stakeholder pyramid: national super admin, state/admin command, police station, parent/public, and NGO.
- Supports public sighting intake, missing-child registration, FIR-style police registration, role-scoped dashboards, case review, match confirmation, and SMS-alert simulation.
- Keeps future face recognition isolated behind `server/src/match.js`, with a stable match-provider contract for the later Aarakshak API.

## Gaps Found And Fixed

- The `/api/reports/found/all` and `/api/reports/found/:id/review` routes were shadowed by `/api/reports/:id`. These routes now resolve correctly before the generic case route.
- Direct case reads and police actions were not checking jurisdiction after lookup by ID. `canAccessReport` now enforces the same scope rules used by list views.
- Parent/NGO report scoping trusted phone-number equality even though demo accounts do not verify phone ownership. Public users now see only reports they created; seeded demo ownership is normalized on startup so the demo parent still sees their own seeded case without exposing cases to a same-phone impostor.
- Public sighting submission returned child names, photos, last-seen details, and report IDs to unauthenticated citizens. The public response now returns only candidate rank, score, age band, gender, and review/referral status.
- Public sighting receipts could not be checked later, forcing citizens to resubmit or contact officials for updates. The system now has a public receipt-status lookup that returns only safe progress, referral, and next-step information without exposing child identity, matched case IDs, reporter contacts, or photo URLs.
- Public sighting intake did not support Mission Vatsalya-style confidential identity or photo-ID proof metadata. Citizens can now mark their identity confidential and provide photo-ID proof type/number; review queues show masked identity/contact details and only a masked proof suffix, while audit events record flags instead of names, phone numbers, or raw ID numbers.
- Public complaints had no Mission Vatsalya-style grievance/feedback channel or reference status tracking. Citizens can now submit grievances with type, report-to level, contact/location, linked case/sighting receipt, and attachment reference; public lookup shows only safe status messages, while operational users get a scoped grievance queue and audited status updates that avoid storing complaint body text in audit metadata.
- Police/admin sighting review was unscoped. `scopeFoundReports` now limits review queues by the matched case jurisdiction, while super admin can see all.
- Unmatched public sightings had no jurisdiction, so every operational role could see them. Public sightings now capture or infer state/district, review queues use that location scope when there is no matched case, and unscoped unmatched sightings stay national-only.
- The dashboard activity feed was global even though cases, sightings, audit, and privacy queues were scoped. Activity events now carry scope metadata, existing seeded activity is backfilled on startup, and `/api/dashboard/activity` is filtered by the same jurisdiction model.
- There was no child-welfare escalation state. Sightings now include 1098/CWC referral fields, and police/admin can refer a sighting to 1098/CWC from the review screen.
- 1098/CWC referral was a handoff without a welfare disposition. Scoped CWC/DCPU/state/command roles can now record a follow-up outcome for unmatched or CWC-referred sightings, such as child located safe, shelter/CCI intake required, police escalation, or duplicate/invalid, with audit/activity history and a safe public receipt-status update.
- Public self-registration allowed users to request privileged police/admin/super-admin roles. Public registration is now limited to parent/public and NGO, and backend hand-posted privileged role attempts are blocked and audited.
- Public citizen/NGO registration did not verify mobile ownership. Registration now requires a demo OTP challenge before account creation, audits OTP start/failure metadata, marks successful public accounts as phone verified, and keeps OTP codes out of audit logs.
- After privileged public signup was blocked, there was no controlled way to create official stakeholder users. Command roles can now provision scoped police, welfare, railway, CCI, JJB, state/crime-bureau, and NGO accounts from the network screen, with jurisdiction checks and audit events.
- Provisioned stakeholder accounts all used the shared demo password. Official account provisioning now creates a unique one-time temporary password, returns it only in the creation response, marks the account for password change, and keeps the secret out of audit metadata.
- Provisioned accounts were marked for password change but could still call protected APIs with the temporary password. Temporary-password users are now forced through password change before dashboard/report workflows, password reuse is rejected, and the change is audited without recording secrets.
- The stakeholder network roster listed every user to command roles even after provisioning was scoped. Network rosters are now scoped: super admin sees all, while state command roles see national plus in-state contacts only.
- Command users could see who existed, but not whether the Mission Vatsalya/TrackChild stakeholder network was complete for a state or district. The network dashboard now includes a scoped coverage report for required state desks and district desks, flagging missing admin/state nodal/crime bureau, police, SJPU, CWC, DCPU, RPF, CCI, and JJB coverage so command teams know what to provision before pilots.
- Stakeholder contacts existed, but command users could not send a scoped, audited coordination alert to police/RPF, welfare institutions, or NGO partners. The network screen now supports scoped network alerts with audience/state/district targeting, recipient previews, activity history, and audit metadata that stores message length rather than the alert body.
- The report-registration API trusted the UI to hide case creation from oversight roles. Backend creation is now restricted to super admin, admin, police, parent, and NGO roles, and public/NGO duplicate warnings no longer expose guardian names or phone numbers.
- Parent/NGO missing-child submissions were treated like operational missing cases immediately. They now enter a citizen/NGO intake-pending state, cannot be confirmed/referred/closed or used for parent alerts until a scoped police/CWC/DCPU/state role verifies the intake, and verification creates a formal FIR/GD number plus audit/workflow history.
- The system had no controlled public missing-child bulletin path even though reference systems emphasize citizen participation and public alerting. Authorized police/state/national roles can now publish or unpublish privacy-safe bulletins only for verified active missing cases, with a public bulletin page that redacts guardian contacts, Aadhar, exact addresses, and protected photos.
- Public discovery was limited to active bulletins, while TrackChild-style systems let citizens search missing/recovered child records. The public bulletin page now includes a privacy-safe public search mode across published missing alerts and anonymized recovered/closed status records, with filters for state, district, gender, age band, and status.
- The internal stakeholder roster helped officials, but citizens had no TrackChild-style public service directory for local response points. A public directory now lists redacted police, CWC, DCPU, RPF, CCI, JJB, and state nodal contacts plus emergency helplines with state/district/role filters, without exposing account emails or internal user state.
- The public directory listed helplines but did not route citizens by emergency context. It now returns a public emergency plan for missing-child, immediate-danger, welfare, and railway/station incidents, prioritizing Childline 1098, ERSS 112, or Railway 139 as appropriate and pairing the helpline with redacted local SJPU/police/CWC/DCPU/RPF desks.
- There was no durable operational audit trail. The system now records scoped audit events for public registration, blocked privileged signup attempts, case/FIR registration, public sightings, CWC referrals, match decisions, and SMS alerts, with a scoped operational audit log screen.
- Audit events could be viewed but not exported as an evidence artifact. Operational roles can now export their scoped audit log as JSON, with an audited `audit.report_exported` event that records only export counts and not the exported event payload.
- The JSON audit log had no tamper-evidence. Audit events now include a hash chain, operational users can verify chain integrity from the audit screen/API, and exports include integrity status while recording only check/export metadata in the audit trail.
- Audit and privacy exports had no artifact signature. Both export payloads now include a deterministic SHA-256 digest plus HMAC signature envelope so pilot teams can verify that a downloaded JSON artifact has not changed after export.
- Signed export artifacts could not be checked after download. Operational roles can now verify audit/privacy export JSON signatures from the API and audit screen, and the verification event records only result metadata, never the uploaded export payload.
- New missing-child reports did not detect likely duplicates. Registration now checks same-scope records using child name, guardian phone, Aadhar, age, gender, and location, returns a 409 duplicate warning with candidates, and requires an explicit audited override before creating a duplicate.
- Photo upload flows did not capture explicit consent, purpose, or retention metadata. Missing-child registration and public sightings now require photo consent when an image is attached, store purpose and retention dates, return retention status to citizens, and show consent/retention data to police reviewers.
- Uploaded child and sighting photos were retrievable from a public URL. The photo endpoint now requires authentication, checks the same report/found-report jurisdiction rules as the rest of the API, and the frontend loads images through authorized blob requests instead of unauthenticated image links.
- The role model did not include key Mission Vatsalya / TrackChild stakeholders. CWC, DCPU, Special Juvenile Police Unit (SJPU), RPF, CCI, JJB, state nodal officer, and crime records bureau roles are now supported with scoped cases, sighting review, privacy review, audit access, public service-directory contacts, and demo logins. Reunification confirmation and SMS remain restricted to police/SJPU/command roles.
- The stakeholder model still missed Anti Human Trafficking Units (AHTU), which are important for trafficking-risk missing-child cases and are listed in Government child-protection stakeholder ecosystems. AHTU is now a district-scoped operational role with demo login, public directory visibility, case/sighting/grievance/audit/MIS access, investigation checklist and external-ID workflows, network provisioning/coverage, and police/SJPU/RPF alert routing, while reunification confirmation remains restricted to police/SJPU/command roles.
- The reference TrackChild workflow includes District Crime Records Bureau (DCRB) users for district-level search, child profile review, alerts, MIS, data publishing, police-station profile mapping, and feedback, but Khozo only had a state crime-bureau role. DCRB is now a district-scoped records role with demo login, public directory visibility, case/sighting/grievance/audit/MIS access, investigation checklist, external-ID and bureau-report workflows, network provisioning/coverage, and records-specific alert routing without reunification-confirmation powers.
- Institutional roles had only passive visibility after being added. Cases now support scoped, audited workflow handoffs for CWC referral, CCI care follow-up, JJB referral, state escalation, and crime records bureau notification without giving those roles reunification-confirmation powers.
- CCI assignment stopped at a generic handoff event. Authorized CWC/DCPU/CCI/state/command roles can now record structured CCI care/admission records with admission type, institution, dates, care plan, next review date, workflow history, and an audit event that intentionally stores only metadata and care-plan length.
- CCI care plans were free-text only even though Mission Vatsalya CCIs track education, vocational training, recreation, health care, counselling, and family tracing. CCI care records now include structured service categories, progress status, and service-progress fields, while audit metadata stores only selected categories and text lengths.
- CCI care records existed only inside individual case drawers, so welfare users lacked a Mission Vatsalya/GHAR-style institutional register. Authorized CWC/DCPU/CCI/state/command roles now have a scoped CCI register with institution counts, active children, admission type split, review due status, and privacy-safe child/case references.
- JJB referral also stopped at a generic handoff event. Authorized JJB/CWC/DCPU/state/command roles can now record structured JJB proceeding records with proceeding type, board name, case number, order date, next hearing date, directions, workflow history, and redacted audit metadata.
- State nodal escalation was only a generic handoff. Authorized state/command roles can now record structured escalation records with escalation type, level, authority, priority, reference number, escalation date, due date, action required, workflow history, and redacted audit metadata.
- Crime-bureau notification was only a generic handoff. Authorized crime-bureau/state/command roles can now record structured NCRB/SCRB reporting records with report type, bureau level, priority, reference number, submission date, next review date, summary, workflow history, and redacted audit metadata.
- Cases had FIR/GD numbers and bureau reports, but no formal way to attach external TrackChild, Khoya-Paya, NCRB/SCRB, CCTNS, GHAR, or state-portal identifiers. Authorized police, RPF, crime-bureau, state, and command roles can now link external IDs to scoped cases with issuing system, issued date, workflow history, duplicate prevention, and audited metadata that omits free-text remarks.
- Citizens and partner agencies could track sighting receipts, but not safely check a missing-child case by FIR/GD or linked TrackChild/NCRB/GHAR reference. A public case-status lookup now resolves Khozo IDs, FIR/GD numbers, and external IDs while exposing only safe progress fields and withholding guardian contacts, identity numbers, exact addresses, photos, notes, care records, and free-text remarks.
- Restoration and repatriation were represented only as final closure labels, so officials could not track the GHAR-style route before closure. Authorized police, welfare, CCI, JJB, RPF, and command roles can now record structured restoration plans with route, target jurisdiction, handover authority, support needs such as interpreter/escort/documents, planned/follow-up dates, workflow history, and redacted audit metadata.
- Restoration plans captured destination and support needs but not the logistics GHAR-style restoration often depends on. Restoration records now track travel mode/date, escort authority/contact, document verification status/reference, and funding source/reference, while audit events store only safe presence/status metadata rather than escort contacts, funding references, document references, or restoration remarks.
- Child-protection welfare services were not tracked as first-class case actions. Authorized CWC, DCPU, CCI, JJB, state, and command roles can now record structured welfare referrals for sponsorship, foster care, adoption facilitation, aftercare, counselling, medical, education, and family strengthening with agency, referral number, review date, workflow history, and audit metadata that stores note length rather than eligibility text.
- Legal services were missing as a child-protection stakeholder even though legal aid, compensation, and court support are part of the official protection ecosystem. DLSA is now a district-scoped operational role with demo login, public directory visibility, scoped dashboards/cases/grievances/audit/MIS access, provisioning/coverage, welfare/legal network alerts, and structured legal-aid referrals for legal aid, victim compensation, court support, counselling/protection-order support, and document/affidavit support with redacted audit metadata.
- Adoption governance was still too generic even though Mission Vatsalya/CARINGS-style workflows distinguish State Adoption Resource Agency and Specialised Adoption Agency responsibilities. SARA and SAA are now scoped operational roles with demo logins, public directory visibility, dashboard/case/grievance/audit/MIS access, provisioning/coverage, adoption network alerts, and structured adoption/CARINGS records for CWC orders, legally-free declarations, CARINGS registration, SAA intake, SARA review, pre-adoption foster care, and follow-up visits with redacted audit metadata.
- Social Investigation Reports and Individual Care Plans were only possible as unstructured case notes. Authorized CWC, DCPU, CCI, JJB, state, and command roles can now record structured case assessments with assessment type, risk level, assessor, assessment/review dates, findings, care plan, recommendation, workflow history, and audit metadata that stores text lengths rather than assessment content.
- CWC/JJB production was not tracked as a timed compliance event. Authorized police, RPF, CWC, DCPU, state, and command roles can now record rescue time, production time, authority, order number, outcome, next action, computed 24-hour deadline status, workflow history, and audit metadata that stores next-action length instead of sensitive text.
- Cases could be escalated but not formally transferred when investigation moved to another district/state. Authorized command roles can now transfer verified open cases to a new jurisdiction, update report scope, preserve transfer history, and audit the previous and new jurisdiction so downstream dashboards immediately reflect ownership.
- Cases had workflow handoffs and jurisdiction transfers, but no accountable owner/desk assignment trail. Scoped operational users can now fetch eligible assignees, assign a verified open case to an in-jurisdiction police/CWC/DCPU/RPF/CCI/JJB/state/crime-bureau/admin owner, preserve assignment history, surface the current owner in the case drawer, and audit assignment metadata without storing assignment-note text.
- Police/SJPU workflows had formal IDs and notes, but no TrackChild-style investigation checklist for the immediate coordination steps after FIR/GD registration. Authorized police, SJPU, RPF, state, crime-bureau, and command roles can now record structured checklist items for FIR/GD, TrackChild, Khoya-Paya, CCTNS, NCRB/SCRB, lookout circulation, railway/RPF, Childline 1098, CWC, media bulletin review, family statement, and last-seen verification, with workflow history and audit metadata that stores selected item codes/counts rather than coordination notes or diary references.
- Handoffs had status changes but no shared case-note chronology for investigation updates, care follow-up, contact attempts, or institutional context. Scoped operational users can now add case notes from the case drawer; notes stay on the case record, appear in recent history, and generate audit/activity events without putting note contents into the audit metadata.
- Recovered cases had no formal TrackChild-style closure outcome beyond a generic found/reunited state. Authorized police/CWC/DCPU/CCI/JJB/state command roles can now close scoped cases with an audited reason such as restored to family, transferred to CCI, adoption/aftercare, repatriated, death recorded, traced pending reunification, or other closure.
- Operational dashboards had counts and activity but no stale-work queue. Scoped follow-up alerts now flag overdue open cases, cases with no recent note/workflow update, old pending sightings, due CCI/JJB/state/bureau/restoration/welfare/case-assessment reviews, and delayed 24-hour production compliance, with high/medium priority surfaced on the dashboard for operational roles.
- Dashboard pending-match counts were global even for scoped operational users. They now use the same scoped sighting queue as the review screen.
- Command dashboards had charts, but no formal TrackChild/Mission Vatsalya-style MIS report artifact. Operational roles now have a scoped MIS report with case/sighting totals, pending intake, public bulletin counts, overdue/stale work, privacy-due totals, age/gender/registration-source splits, production-compliance counts, formal follow-up due counts, state/district breakdowns, workflow action counts, recent audit activity, and an audit event for every report generation.
- Command users had no explicit production-readiness/preflight view to separate demo capabilities from launch blockers. The operational overview now includes a readiness report covering JSON storage, audit-chain integrity, export signing, OTP delivery, Aarakshak/match-provider status, public-abuse monitoring, offline queue support, and automated verification coverage.
- MIS reports were generated and audited but were not tamper-evident downloadable artifacts like audit/privacy exports. MIS responses now include the same SHA-256/HMAC signature envelope and can be verified through the export verifier, including tamper detection.
- Retention metadata had no operational follow-up. A scoped privacy review queue now lists case and sighting retention status, lets authorized operational roles mark records reviewed or extend retention, and audits every retention decision.
- Retention expiry had no execution path or export. Authorized operational roles can now anonymize case/sighting personal data from the privacy queue only with an approval/order reference, preserve that approval evidence in audit/export metadata without storing approval-note text, and export scoped privacy reports with totals and record-level retention status.
- Privacy actions used one broad operational role list for viewing, mutation, anonymization, and export. Privacy access is now split by capability: operational users can view scoped retention status, CWC/DCPU/police/state command can review or extend, only command privacy roles can anonymize, and only command/crime-bureau roles can export scoped privacy reports.
- Public field reporting had no low-connectivity recovery. The capture flow now saves failed sighting submissions in an encrypted IndexedDB queue on the device, registers a service worker, requests background sync where supported, retries on reconnect, and still lets users manually retry or remove pending reports.
- The demo face-match boundary was implicit. `server/src/match.js` now exposes match engine metadata (`demo-local`, non-biometric) so the UI and audit trail are honest today and Aarakshak can be wired in later behind the same contract.
- Text-only citizen sightings could trigger random demo match candidates because the scorer fell back to randomness without a photo. Text-only sightings now require useful details, skip match ranking, and go directly to Childline/CWC intake with a clear public receipt.
- Missing-child and public sighting intake trusted client-side form limits for ages, dates, phone numbers, coordinates, gender values, and uploaded file types. Server-side validation now rejects impossible child ages, future missing dates, invalid contact/geo fields, unsupported genders, overlong sighting text, and non-image uploads before records enter the investigation queue.
- Missing-child registration lacked TrackChild/Form-J style identification and vulnerability fields. The FIR/intake form now captures structured physical identifiers, clothing, languages, produced-by source, education, disability/mental-health support flags, vulnerability categories, and circumstances; operational users see the profile in the case drawer while public status/search/bulletin payloads remain redacted and audit metadata stores only safe profile flags/categories.
- Missing-child FIR/intake registration captured consent for photos, but not a formal reporter declaration. Every missing-child report now requires a reporter/guardian/officer declaration with signer, relationship/designation, declaration method, acceptance time, and statement version; operational users can see the declaration status while public lookups and audit metadata avoid storing signer text.
- Public registration, login, and citizen sighting intake had no abuse throttle. Lightweight fixed-window rate limits now protect these open endpoints, return `429` with retry metadata, and keep limits configurable for pilot deployments.
- Public status lookups for grievances, sightings, case/FIR references, and public bulletins could be enumerated without throttling. These public lookup surfaces now have dedicated configurable fixed-window limits with `429` retry metadata, reducing receipt/FIR/external-ID probing risk while preserving citizen access.
- Open public intake surfaces had rate limits and audit events, but no monitored command queue for abuse review. Rate-limit breaches, OTP failures, and blocked privileged-signup attempts now feed a command-only public abuse queue with severity, 4-hour/24-hour SLA status, limiter/source counts, hashed public identities instead of raw IPs, phones, FIRs, or receipt IDs, audited analyst dispositions for reviewed/escalated/dismissed signals without storing note text in audit metadata, safe operational activity entries for escalated signals, and signed redacted exports for SOC/SIEM handoff.
- Dashboard navigation hid unauthorized sections, but deep-linked URLs could still mount those screens and rely on API failures. Frontend dashboard routes now use shared role metadata for both navigation and route-level guards, with an explicit restricted-access state for out-of-role users.
- Critical security and workflow behavior was only manually smoke-tested. The repo now has `npm run smoke:api`, a repeatable API smoke suite that starts an isolated API port, backs up/restores `db.json`, and checks scoped dashboards, text-only sightings, CWC workflow permissions, privileged provisioning, and audit events.

## Remaining High-Value Improvements

- Add production-grade data storage, audit immutability, and Aarakshak integration before a live multi-agency pilot.
- Replace the JSON store with Postgres or SQLite before multi-user pilot testing.
- Expand smoke coverage into a full automated test suite for report registration, privacy export/anonymization, duplicate overrides, and browser-rendered route access.
- Move the tamper-evident JSON audit log into the production database with immutable append-only storage and hardware/managed-key signed export verification.
- Replace demo anonymization with production-grade deletion/anonymization jobs, multi-approver workflow, evidence attachments, and managed-key signed exports.
- Add real Aarakshak face recognition integration behind `server/src/match.js`, returning ranked matches plus provider, model version, biometric flag, and confidence metadata.
- Extend duplicate detection with face embeddings once the Aarakshak recognition API is connected.
- Add a full PWA manifest/install experience and production hardening for the service-worker-backed offline queue, including operational sync telemetry and remote wipe/expiry policy for abandoned field devices.
- Add stronger production abuse controls: real SMS gateway OTP, CAPTCHA, device fingerprinting, WAF rules, escalation notifications, automated SIEM forwarding, and case-management integration for the public abuse queue.
